1. Project at a Glance

The Accessibility Auditor checks a web page for common accessibility mistakes: images without alternative text, text that is too faint to read, form fields with no label, buttons with no name, broken heading order, and misuse of ARIA attributes. It reports each problem with the exact element that caused it, gives the page a score out of 100, and exports the result in three formats.

2. What This Project Does

2.1 For the user

  1. The user enters a URL in the command line or the web app.
  2. The tool opens that page in a real browser, exactly as a visitor would see it.
  3. It runs dozens of accessibility rules against the rendered page.
  4. It groups the failures by severity and calculates a score out of 100.
  5. It shows each failed rule with the CSS selector and HTML of every affected element.
  6. The user downloads the result as Markdown, printable HTML or JSON.

2.2 Features built into the tool

FeatureWhat it gives the user
Command-line interfaceOne command, reports written to a folder. Easy to put in a script or CI pipeline.
Streamlit web appType a URL, press a button, see the score and expand each issue in the browser.
Severity filterHide minor issues and focus on critical and serious barriers first.

2.3 Behind the scenes, in one paragraph

The scanner uses Playwright to start a headless Chrome browser and open the URL. After the page settles, it injects the axe-core JavaScript file into the page and asks it to inspect the whole document. axe-core returns a structured list of failed rules. The Python code reduces that large response to the fields it needs, converts it into simple data objects, calculates the score, and passes the result to three report writers. Finally the browser is closed and the files are saved. Nothing is uploaded anywhere.

In simple words It is a browser robot that opens a page, runs an accessibility checklist on it, and writes down what is wrong and where.

3. Why It Matters

The web is how people apply for jobs, pay bills, study, book appointments and reach government services. When a page is built without accessibility in mind, some people are simply locked out — not because they lack the ability, but because the page was not built for them.

The World Health Organization estimates that about 1.3 billion people, roughly 16% of the world, live with significant disability. Add temporary conditions such as a broken wrist or a bright screen in sunlight, and the number of people who benefit from accessible design is far larger.

3.1 Common barriers and who they affect

BarrierWho is blocked
Image with no alt textA blind user hears “image” instead of the information the image carries.
Text with low contrastPeople with low vision, colour blindness, or anyone using a phone in sunlight.
Form field with no labelA screen reader cannot say what the field is for, so the user has to guess.
Button with no nameThe control is announced as just “button”. The user cannot tell what it does.
Heading levels out of orderScreen reader users navigating by headings lose the structure of the page.
Content unreachable by keyboardPeople who cannot use a mouse cannot operate the page at all.
Zoom disabledPeople who need larger text are prevented from enlarging it.

3.2 The legal side

  • WCAG 2.2 is the current Web Content Accessibility Guidelines recommendation from the W3C, published in 2023.
  • India: the Rights of Persons with Disabilities Act, 2016 requires accessible public digital services.
  • European Union: the European Accessibility Act applies to many digital products and services from June 2025.
  • United States: the Americans with Disabilities Act has been applied to websites in many court cases.

Laws differ by country and by sector. This project does not give legal advice, and a good score is not a statement of legal compliance.

The honest problem Automated tools find only part of the problem. They are excellent at catching mechanical mistakes such as missing alt text, but they cannot judge whether the alt text makes sense, whether the reading order is logical, or whether a screen reader announces the page clearly. This project is a first filter, not a replacement for human testing.

4. What Accessibility Means in Practice

WCAG organises accessibility into four principles, often remembered as POUR. They are a useful way to understand why the rules in this project exist.

PrinciplePlain meaningExample problem this tool catches
PerceivableThe user must be able to sense the content.An image with no text alternative; grey text on white with a contrast ratio below the minimum.
OperableThe user must be able to use the controls.A clickable <div> that cannot be reached with the keyboard; zoom disabled in the viewport tag.
UnderstandableThe page must behave predictably and be readable.A missing page language; headings that jump from level 1 to level 4.
RobustThe page must work with different browsers and assistive technology.Invalid ARIA roles; ARIA roles placed inside the wrong parent element.

4.1 WCAG conformance levels are not the same as impact levels

WCAG defines three conformance levels: A (minimum), AA (the usual legal target) and AAA (enhanced). The tool does not claim a conformance level. Instead, each failed rule is labelled with axe-core’s own urgency rating:

ImpactWhat it means here
CriticalA barrier that can stop some users completely, such as a control with no name.
SeriousA significant barrier that makes the page hard or confusing to use.
ModerateA real problem that adds friction but usually leaves a workaround.
MinorA small issue, often about polish or best practice.
Why this distinction matters “Impact” answers “how badly does this hurt a user?”. “Conformance” answers “does this page meet a specific WCAG success criterion?”. They are related but not identical. This tool reports the first and never claims the second.

4.2 What a good result actually looks like

A page with no automated violations is a good sign, not a certificate. A responsible workflow is: fix what the tool finds, then test with a keyboard, then test with a screen reader, then ask a real user to try a task. This project automates the first step well and says so clearly.

5. How the Scanner Works

5.1 Why a real browser is needed

Many accessibility problems only exist after the browser has built the page. A modern site may render its menu with JavaScript, load fonts late, or set colours in a stylesheet. A simple HTML download would miss all of that. Playwright drives an actual Chrome or Edge browser, so the tool checks the page in the same state a user sees.

5.2 What axe-core is

axe-core is an open-source accessibility testing engine made by Deque Systems, licensed under the Mozilla Public License 2.0. It is the same engine used behind Lighthouse’s accessibility audit and by many commercial testing tools. It contains dozens of rules covering images, forms, colour contrast, ARIA, document structure, tables and best practices.

Version 4.14.0 is stored inside the project at a11y_auditor/vendor/axe.min.js (about 637 KB). Keeping a local copy means a scan never fails because a content delivery network is down or blocked, and the exact rule set is reproducible.

5.3 The scan, step by step

1. Start a browser
Playwright launches installed Chrome, Edge, or bundled Chromium in headless mode

2. Open the URL
Desktop viewport 1366 × 900 · configurable timeout · waits for the load event
▼
3. Let the page settle
Extra wait (1.2 s by default) for late JavaScript, fonts and lazy content

5.4 Robustness decisions

DecisionReason
Try the requested browser, then fall backIf Chrome is not installed, the tool still works with Playwright’s own Chromium, with a clear error if neither exists.
Script-tag injection with an eval fallbackSome sites use a Content Security Policy that blocks added script files.
Refuse to score bot-protection pagesA CAPTCHA page is not the site. Scoring it would produce a false result.
Cap stored elements per ruleA page with 200 broken images should not send a giant result across the browser boundary or flood the report.
Close the browser in a finally blockProcesses are cleaned up even when a scan fails.
In simple words The tool does not guess from the HTML source. It opens the page in a real browser, lets it finish loading, then runs a professional accessibility checklist inside the page.

6. The Checks It Runs

The tool runs every rule that axe-core enables by default, including WCAG 2.0, 2.1 and 2.2 rules and best-practice rules. The table below groups the most important ones by what a user experiences.

AreaExample ruleWhat it catches
Imagesimage-altAn informative image with no alt text, or a decorative image that is not marked as decorative.
Colourcolor-contrastText whose contrast ratio against its background is too low for normal reading.
FormslabelAn input with no programmatic label, so a screen reader cannot announce its purpose.
Control namesbutton-name, link-nameA button or link with no readable text or accessible name.
Structureheading-order, regionHeadings that skip levels; page content that sits outside any landmark region.
ARIAaria-required-parentAn ARIA role used in a place where it cannot work, such as a tree item outside a tree.
Keyboardscrollable-region-focusableA scrollable area that cannot be reached or scrolled with the keyboard.
Document basicshtml-has-lang, frame-titleA page with no declared language; an iframe with no title.
Tablestd-headers-attrData tables whose header cells are not connected to the data cells correctly.
Zoom and viewportmeta-viewportA page that disables pinch zoom or sets a maximum scale.

6.1 What the tool reports for each failure

  • Rule id and title — for example image-alt, “Images must have alternative text”.
  • Impact — critical, serious, moderate or minor.
  • Description and documentation link — so the developer can read the full rule.
  • WCAG tags — which success criteria the rule maps to, when applicable.
  • Affected elements — a CSS selector and a short HTML snippet for each one.
  • Failure summary — axe-core’s short explanation of what to change.

6.2 What it does not report

A rule that passes is counted but not listed in detail. Rules marked “incomplete” by axe-core are counted separately, because the engine could not decide automatically. The report shows that count so the user knows a human should look.

Important Automated rules check what can be expressed as a machine rule. They cannot tell whether an alt text is useful, whether the tab order is logical, or whether an error message is understandable. Those need a person.

7. The 0–100 Score

The score is a summary, not a measurement of WCAG compliance. It exists so a team can see progress and compare pages. The formula is deliberately simple enough to explain to a non-technical person.

7.1 Step one: what each failed rule costs

ImpactPoints per ruleMost it can cost in total
Critical1050
Serious630
Moderate315
Minor15

7.2 Step two: count affected elements, but stop at three

Each rule’s cost is multiplied by the number of affected elements, but never by more than three. A page with 200 images missing alt text therefore costs the same as a page with three. Without this limit, one repeated mistake would hide every other problem on the page.

7.3 Step three: cap each severity

Even a page with 30 critical rules should not automatically score zero, because zero hides everything the page gets right. Each severity can only take away the maximum shown in the table above. The four caps add up to 100, so a score of 0 is still possible when every category is saturated.

7.4 Step four: subtract and grade

score = max(0, 100 − total deduction). The letter grade follows:

GradeScoreMeaning used by the tool
A90–100Good — only minor problems found.
B80–89Fair — several issues should be fixed.
C70–79Needs work — real barriers for some users.
D60–69Poor — many users will struggle.
F0–59Failing — serious barriers across the page.

7.6 Why the caps exist

The first version of the score had no severity caps. When tested against python.org, it returned 0/100 from seven failed rules. That number was technically consistent but useless: it told the reader nothing about which problems were worse, and it made any improvement invisible. The caps were added after that test, and the same page then scored 17/100. Still poor, but informative.

The caps are a product judgement, not an accessibility standard. The report and README both say so. The grade is a progress indicator, not a compliance verdict.

In simple words Start at 100. Take away points for each kind of mistake, with worse mistakes costing more. Stop counting repeats after three examples of the same mistake, and stop one category from wiping out the whole score. Then turn the number into a letter.

8. The Reports

A scan produces up to three files, all from the same result object. They contain the same facts, formatted for different readers.

FormatBest forWhat it contains
MarkdownGitHub issues, pull requests, README notesSummary, severity table, one section per violation, element selectors and HTML snippets.
HTMLSharing with a client or printing to PDFA self-contained page with styling, score cards, severity table and every violation. No internet needed.
JSONOther tools, dashboards, automationStructured data: URL, title, timestamp, score, grade, counts, and a full array of violations and elements.

8.1 What every report includes

  • The page URL and title, plus the scan date and duration.
  • The score, grade and a one-line verdict.
  • Counts of failed rules, affected elements, passed rules and checks needing review.
  • A severity breakdown: critical, serious, moderate, minor.
  • Every violation sorted from worst to least severe, then by number of affected elements.
  • For each violation: the rule, its impact, a description, a documentation link, WCAG tags, and each affected element.
  • The honest footer: automated checks catch only part of the problem.

8.2 Printable HTML instead of a separate PDF library

The HTML report is designed to print cleanly on A4. Instead of adding a heavy PDF dependency, the project tells the user to open the HTML file and choose Print → Save as PDF. That keeps the dependency list small and the output predictable. The repository includes a real sample at docs/sample-report.html.

Design choice The reports never say “this page is WCAG compliant”. They say what was checked, what failed, and what a human should still verify. That restraint is deliberate.
In simple words One scan gives you a GitHub-friendly text report, a polished page you can print or send, and a data file that other software can read.

9. Real Scans and What They Show

These are real results from the finished tool. They are included because a portfolio project should show evidence, not only claims.

PageScoreGradeRules failedWhat was found
examples/bad-page.html (deliberately broken) 47F9 (18 elements) Missing button name, missing alt text, low contrast, no page language, empty link, heading jump, missing landmarks, zoom disabled, content outside landmarks.

9.1 Reading the results honestly

A low score does not mean a site is unusable. The python.org result is driven by its hidden navigation: items carry the ARIA role treeitem without a surrounding tree, and the same kind of issue repeats many times. That is a genuine bug worth fixing, but most sighted visitors never notice it. The report lists the exact elements so a developer can judge.

Equally, a high score is not proof of quality. example.com is a deliberately tiny page. It cannot demonstrate good form design, keyboard flow or screen reader behaviour because it has none of those things.

9.2 A scan that refused to produce a result

The W3C’s intentionally bad demo page was an obvious test target. When scanned, it returned a Cloudflare page titled “Just a moment…” instead of the real content. The first version of the tool happily reported “1 critical issue, score 90” against the CAPTCHA screen. That was a false result.

The fix was a guard: if the page title matches a known bot-protection screen, the scan stops with a clear message and exit code 2. It is a small feature, but it shows the difference between producing a number and producing a trustworthy number.

In simple words The tool was tested on a broken demo page, a tiny clean page and a large real website. It also learned to refuse when a website blocks robots, instead of inventing a score.

11. How to Run It

11.1 What you need first

  • Python 3.10 or newer.
  • Google Chrome or Microsoft Edge installed, or Playwright’s own Chromium.
  • Internet access for the page you want to scan (the tool itself runs locally).

11.2 Setup

  1. Open a terminal in the project folder.
  2. Create a virtual environment: python -m venv venv
  3. Activate it: venv\Scripts\activate on Windows, or source venv/bin/activate on macOS / Linux.
  4. Install the packages: pip install -r requirements.txt
  5. Optional: install the package itself with pip install -e . to get the short a11y-auditor command.

If Chrome and Edge are missing, run playwright install chromium and pass --browser "" to use the bundled browser.

11.3 Scan from the command line

Basic use:

python -m a11y_auditor.cli https://example.com

Useful options:

OptionWhat it does
--out DIRWhere to write the reports. Default: reports.
--format md,html,jsonChoose any combination of formats.
--browser chromeChoose chrome, msedge, or an empty string for bundled Chromium.
--timeout 30000Page load timeout in milliseconds.
--wait 1200Extra settle time after load, for late JavaScript.
--fail-under 90Exit with code 1 if the score is below 90. Useful in CI.
--quietPrint only the summary, not every violation.

11.4 Scan from the web app

streamlit run app.py

The app opens at http://localhost:8501. Enter a URL, press Scan page, then filter by severity and download any report format.

12. Engineering Quality: Tests and CI

A working demo is not the same as a maintained project. Two things separate this project from a script that happens to run: the tests and the continuous integration pipeline.

12.1 The 29 tests

Test fileTestsWhat is verified
test_scoring.py12Perfect page scores 100; each impact costs the right points; the three-element cap works; severity caps work; all categories saturated reaches 0; unknown impact falls back safely; grade boundaries; counts use rules not elements; every impact key always exists.
test_report.py9JSON has the expected fields and correct counts; violations are sorted worst-first; a clean page scores 100; JSON round-trips; Markdown contains the key sections; empty results are worded correctly; HTML escapes page content; HTML is a standalone document.
test_cli.py8File names keep dots in host names; schemes and trailing slashes are handled; file URLs use the file name; report paths are correct; long URLs are shortened; empty slugs fall back; bad formats are rejected before any scan.

The tests use synthetic data only. They need no network, no browser and no axe-core run, so the suite finishes in under a second and can run anywhere. That is a deliberate trade-off: the logic is tested thoroughly, while the browser scan is verified manually against real pages.

12.2 Continuous integration

The GitHub Actions workflow runs on every push to main and on every pull request. It installs Python 3.11, installs the dependencies, and runs pytest. A green badge on the README is a live signal that the tests still pass, not a screenshot pasted into the document.

12.3 Two real bugs the testing caught

In simple words The maths and the reports are checked automatically every time the code changes. The browser part is checked by hand. The tests already caught two real mistakes, including one that only appeared on a different computer.

14. Limitations (Honest List)

Every tool has limits. Writing them down is part of building trust. These are the real limits of this version, not hypothetical ones.

LimitationWhat it means in practice
Automation finds only part of the problemCommon estimates say automated checks catch roughly 30–50% of real accessibility issues. The rest needs human judgement.
Only the loaded state is checkedContent behind a login, a click, a menu, a modal or infinite scroll is not reached.
No keyboard or screen reader testingThe tool cannot judge tab order, focus traps, announcements or reading flow. Those still need a person.
The score is a heuristicThe weights and caps are product decisions, not a WCAG formula. A high score is not a compliance certificate.
One page per scanNo crawling, no sitemap, no site-wide summary. Each URL is a separate scan.
Content inside iframes is missedaxe-core runs on the main document. Frames would need separate injection and are not covered yet.
No screenshotsIssues are described with selectors and HTML snippets, not pictures of the problem.
No login or session supportPrivate pages behind authentication cannot be scanned.
Some sites block automationBot protection produces a refusal to score. That is safer than a false result, but it means the site cannot be checked.
Timing can change the resultJavaScript-heavy pages may still be loading. The extra wait is configurable, but it is not a guarantee.
Rule set is pinnedaxe-core 4.14.0 is fixed in the repository. New rules and fixes arrive only when the vendored file is updated.
No browser test in CIThe scan path is verified manually; the automated suite covers scoring, reports and file naming.
Not deployedBoth interfaces run locally. There is no hosted demo or public API.
No PDF writerPDF is produced by printing the HTML report, not by a dedicated PDF library.
No legal or compliance claimThe tool cannot certify WCAG conformance and does not try to.
In simple words It is a strong first filter, not an accessibility expert. It catches the mechanical mistakes quickly and tells you where they are. A person still has to use the page with a keyboard and a screen reader to find the rest.

15. Future Improvements

15.1 Highest impact first

  1. End-to-end test with a local page. Add a fixture page to the repository, install Chromium in CI, and assert the exact violations and score. This closes the largest testing gap.
  2. Crawl mode. Accept a start URL, follow internal links up to a depth and page limit, and produce a site-wide summary.
  3. Screenshots per issue. Use Playwright to capture the affected element and embed the image in the HTML report. A picture is faster to understand than a selector.
  4. Baseline comparison. Save a scan, then compare the next one and show what was fixed, what is new and what remains.

15.2 Next

  1. SARIF export. A format GitHub code scanning understands, so issues appear in the security tab automatically.
  2. Ready-made GitHub Action. Let other repositories run the auditor with a few lines of YAML.
  3. Interactive states. Allow a small script of clicks before the scan, so open menus and dialogs are checked too.
  4. Iframe support. Inject axe-core into each frame and merge the results.

17. The Complete Algorithm — Explained for HR

This final section is written for a non-technical reader. No prior knowledge is assumed. Every step is one action. Nothing is skipped.

17.1 The one-minute explanation

“I built a tool that checks whether a website is usable by people with disabilities. You give it a web address, and it opens the page in a real browser, the way a visitor would see it. It then runs a professional accessibility checklist and finds problems such as images with no description, text that is too faint to read, or buttons with no name. It groups the problems by how serious they are, gives the page a score out of 100, and writes a report that shows the exact element that needs fixing. It works from the command line and from a simple web page. I also wrote tests and set up automatic testing on GitHub, and I documented clearly what the tool cannot catch.”

17.2 Algorithm A — How the system was built (from zero)

StepActionWhat it means
1Understand the problemLearn what makes a website hard to use for people with disabilities, and why manual checking does not scale.
2Choose the scopeCheck one page at a time, report what can be detected automatically, and do not pretend to replace human testing.
3Choose an engineUse axe-core, a trusted open-source accessibility engine, instead of inventing rules from scratch.
4Make it reliableStore axe-core inside the project so a scan does not depend on an external website.
5Choose a browser driverUse Playwright so the page is rendered by real Chrome, including JavaScript content.
6Design the dataDefine three simple objects: one affected element, one failed rule, one complete result.
7Build the scannerOpen the page, wait for it to settle, inject axe-core, run the rules, and convert the result into those objects.
8Handle real-world problemsAdd a script fallback for strict security policies, a browser fallback, timeouts, and a guard against CAPTCHA pages.
9Design the scoreGive points per severity, count repeats up to three, cap each severity, subtract from 100, and map to a letter grade.
10Build the reportsWrite one result as Markdown, printable HTML and JSON from a single shared function.
11Build the command lineAccept a URL, folder, formats, browser and timeout; validate the input; write the files; support a failure threshold.
12Build the web appAdd a URL box, a scan button, score cards, a severity filter, expandable issue details and download buttons.
13Write testsCheck the scoring maths, the report content, the HTML safety and the file naming, using synthetic data.
14Add continuous integrationRun the tests automatically on every push and pull request, and show a green badge.
15Test on real pagesScan a deliberately broken demo page, a tiny clean page and a large real website; fix what the results reveal.
16Document and publishWrite the README, licence, package metadata and honest limitations, then release the code on GitHub.

17.3 Algorithm B — What happens when a user scans a URL

StepActionWhat it means
1User enters a URLThe command line or web app receives the address.
2Check the inputThe app rejects an empty address or one without http:// or https://.
3Start a browserPlaywright launches Chrome, Edge or bundled Chromium in the background.
4Open the pageThe browser loads the address and waits for the page load event, up to the timeout.
5Wait a momentExtra time lets late JavaScript, fonts and images finish appearing.
6Check the titleIf the page is a bot check or CAPTCHA, stop with a clear message rather than scoring it.
7Load the checklistInsert axe-core into the page; if the site blocks it, run the source directly as a fallback.
8Run the rulesaxe-core inspects the rendered document and returns every failed rule and affected element.
9Reduce the resultKeep only the useful fields: rule, impact, explanation, tags and element details.
10Calculate the scoreApply the weights, the three-element limit and the severity caps; produce the score and grade.
11Build the reportsRender Markdown, HTML and JSON from the same result.
12Show and saveThe terminal prints a summary and file paths; the web app shows metrics and download buttons.
13Close the browserThe browser is always closed, even if an error occurred.

17.4 Algorithm C — How the score is calculated (step by step)

StepActionWhat it means
1Start with 100 pointsThe page is assumed perfect until a rule proves otherwise.
2Take one failed ruleLook at its impact label: critical, serious, moderate or minor.
3Find its weightCritical is 10, serious is 6, moderate is 3, minor is 1.
4Count affected elementsCount how many elements break that rule, but never count more than three.
5MultiplyWeight × counted elements = points for that rule.
6Add to its severity bucketKeep a separate running total for critical, serious, moderate and minor.
7Repeat for every ruleEvery failed rule contributes to its own bucket.
8Apply the severity capsCritical can take at most 50, serious 30, moderate 15, minor 5.
9Add the capped bucketsThis is the total number of points removed.
10Subtract from 100Never go below zero. The result is the score.
11Assign a grade90+ is A, 80+ is B, 70+ is C, 60+ is D, below 60 is F.
12Write a verdictOne plain sentence explains what the score means.

17.5 How to say it in an interview (five points)

  1. The problem: many websites lock out people with disabilities, and the people who build them usually cannot see the problem.
  2. The approach: use a trusted accessibility engine inside a real browser, then turn its output into a score and an actionable report.
  3. The engineering: separate scanning, scoring, reporting and interfaces; package it; test the maths and reports; run the tests automatically on GitHub.
  4. The product: give both a command line for automation and a web page for people, with severity filters and three export formats.
  5. The honesty: state that automation catches only part of the problem, document every limitation, and never claim WCAG certification.
If asked to explain it in one sentence “It is a quality-check tool for websites: it opens a page like a real visitor, runs a professional accessibility checklist, and tells you what is broken, how serious it is and where to fix it — while being clear about what still needs a human.”
